# Design: Integrate Understand-Anything into j-stack

Generated by /office-hours on 2026-05-28
Branch: main

Mode: Builder

## Problem Statement

j-stack runs an opinionated phase pipeline (EXPAND → REFINE → SURVEY → PLAN → BUILD → POLISH → DEFEND → HANDOFF) but has a blind spot: when a session starts on an **existing codebase**, the only orientation tool is reading files and `git log`. There is no structured way to surface architecture, dependencies, business flows, or "what does this 200k LOC project actually do" before a phase begins.

Understand-Anything (Lum1104, 42k★, MIT) produces exactly that artifact: a knowledge graph of files/functions/classes/dependencies plus a domain-flow view, served as an interactive dashboard. It already ships as a Claude Code plugin and has installers for Codex, Cursor, Copilot CLI, Gemini CLI, OpenCode, etc. — the same cross-tool surface j-stack already serves.

The integration question is **where in the phase pipeline does it slot, and how deep does j-stack wire it in** — bundled-and-mentioned, phase-aware-wired, or wrapper-skill-with-wiki-integration.

## What Makes This Cool

The two systems are oddly complementary:

- j-stack's `.planning/` wiki is a **Karpathy-pattern markdown wiki** — exactly what Understand-Anything's `/understand-knowledge` is designed to ingest. You can point Understand-Anything at j-stack's own wiki and visualize the engagement as a graph.
- Understand-Anything's `/understand-diff` (ripple analysis pre-commit) maps cleanly to j-stack's POLISH phase.
- Understand-Anything's `/understand-onboard` (auto-generated onboarding guide) maps cleanly to j-stack's HANDOFF phase.
- session-start's existing-repo intake already asks "Is there existing documentation?" — if the answer is no, j-stack can manufacture the answer.

This is not "bolt a tool on." This is filling a gap j-stack actually has.

## Constraints

- Understand-Anything has its own installer (`install.sh`/`install.ps1`) and plugin registry — do not re-vendor or reproduce. Chain into the upstream.
- MIT license, no attribution constraints beyond standard.
- Understand-Anything output lives in `.understand-anything/knowledge-graph.json` — keep it there, do not relocate.
- j-stack's stack-ownership rule (one skill per phase) must not be violated. Understand-Anything's commands augment phases, they do not replace them.
- Must not break j-stack's existing install flow (`bash install.sh`).

## Premises

1. **Understand-Anything is best used as an augmentation, not a replacement.** prior-art-survey still owns scouting OSS/libraries/patterns; Understand-Anything owns visualizing the *current* codebase. They are different artifacts.
2. **Phase-wiring beats install-and-forget.** A bundled tool that nobody invokes is wasted leverage. j-stack should reference `/understand` from the skills where it actually helps (session-start, prior-art-survey, handoff-snapshot, stakeholder-pack).
3. **The Karpathy-wiki bridge is a real feature, not a curio.** Running `/understand-knowledge .planning/` on the wiki itself is a novel use case worth surfacing.
4. **Bundling is opt-in, not mandatory.** install.sh should offer an `--with-understand-anything` flag (or a yes/no prompt) so users who don't want the dependency can skip it.

## Approaches Considered

### Approach A: Light-touch — bundle in install.sh + document in CLAUDE.md

Add a Phase 2.6 to `install.sh` that runs Understand-Anything's upstream installer (with `--platform claude` for native plugin install) behind an opt-in flag. Append a "Code comprehension" section to the global and project CLAUDE.md that mentions `/understand` and lists when to use it. No changes to existing skills.

- **Effort:** S (1-2 hour edit to install.sh + CLAUDE.md sections)
- **Risk:** Low — purely additive, no skill changes
- **Pros:** Fastest. Respects upstream tool boundaries. Zero risk of breaking existing skills. Easy to remove.
- **Cons:** Most leverage is left on the table — users have to remember to invoke /understand themselves. The "phase pipeline aware" promise of j-stack is not extended to the new tool.
- **Reuses:** install.sh's existing Phase 1/2/2.5 pattern.

### Approach B: Phase-wired — bundle + update relevant skills (RECOMMENDED)

Approach A plus targeted edits to four skills:

- **session-start.SKILL.md** — In the existing-repo intake, after Q4 ("existing documentation?"), if the user has no docs, offer: "Run `/understand` to bootstrap an architecture graph for this codebase?" If yes, run it before continuing orientation.
- **prior-art-survey** — After the OSS/library/patterns scouts return, if the engagement is **forking or extending** an existing codebase, run `/understand` on the candidate repo and file the graph into `.planning/prior-art/`.
- **handoff-snapshot.SKILL.md** — Include the path to `.understand-anything/knowledge-graph.json` (if it exists) in the handoff snapshot, so the next tool/session can read the graph.
- **stakeholder-pack.SKILL.md** — Add a "Codebase visualization" section that links to the graph and offers to include the dashboard screenshot in the executive pack.

- **Effort:** M (install.sh edit + 4 skill edits + CLAUDE.md updates ≈ half a day)
- **Risk:** Low-Medium — skill edits are surgical, but each adds a new branch users will hit
- **Pros:** Real leverage. j-stack becomes phase-aware about codebase comprehension. The session-start hook in particular is high value — first impressions of an unfamiliar codebase shape the whole engagement.
- **Cons:** Four files to keep in sync with Understand-Anything's CLI surface. If Lum1104 renames `/understand-diff`, j-stack's references break.
- **Reuses:** Existing skill structure; install.sh pattern; CLAUDE.md sections.

### Approach C: Deep wrapper — add a `understand-codebase` j-stack skill

Approach B plus a new j-stack skill that wraps `/understand` and files its output into the wiki (`.planning/raw/codebase-graph-{date}/` with a one-line summary in `index.md`). Adds a `## Codebase Graph` section to `index.md`. Treats the graph as a first-class wiki artifact that compounds with the rest.

- **Effort:** L (Approach B + new skill ≈ 1-2 days including testing across tools)
- **Risk:** Medium — wrapper skill duplicates upstream functionality and creates a maintenance surface. If Understand-Anything changes its output schema, j-stack's wrapper has to follow.
- **Pros:** Full wiki integration. The knowledge graph becomes a tracked artifact like any other reviewed output. Compounds with handoff-snapshot, stakeholder-pack, second-opinion.
- **Cons:** Most code; biggest maintenance surface; arguably solving a problem that doesn't exist yet — the wiki already files things, no wrapper needed.
- **Reuses:** poc-wiki-init's wiki-write pattern; install_skill helper in install.sh.

## Recommended Approach

**Approach B — phase-wired bundling.** A is too thin to justify the integration (users won't invoke /understand without prompting); C is over-engineered until we see the wrapper actually pulling its weight. B captures the real leverage points (session-start + handoff in particular) at a half-day cost and stays additive to all existing skills.

## Open Questions

- **Opt-in default:** should install.sh enable Understand-Anything bundling by default (`--skip-understand-anything` to opt out) or off by default (`--with-understand-anything` to opt in)? Default-on maximizes adoption but adds an external dependency to a flow that's currently self-contained. Recommendation: default-off, with a clear prompt during install asking the user to choose.
- **Wiki bridge as a launch feature:** should the README highlight "run /understand-knowledge on your own .planning/ wiki" as a flagship feature, or keep it as a footnote? It's a genuinely novel use case but might confuse first-time users.
- **Version pinning:** Understand-Anything is actively developed (commits weekly). Should j-stack pin to a specific tag/SHA in install.sh, or always pull main? Pin reduces surprise breakage; main keeps users on latest. Recommendation: pin to a tag, document the upgrade flow.

## Success Criteria

- `bash install.sh` cleanly installs Understand-Anything alongside j-stack's existing skill set (no conflicts, no broken paths).
- session-start, when entering an existing repo with no docs, offers `/understand` and the user can accept/decline without breaking the orientation flow.
- handoff-snapshot includes a `## Codebase graph` line pointing to `.understand-anything/knowledge-graph.json` when present.
- README documents the integration in ≤ 1 paragraph including the wiki-bridge use case.
- A second-opinion review (Codex) on the install.sh diff returns no blocking concerns.

## Distribution Plan

j-stack is distributed via `bash install.sh` from the cloned repo. The integration ships through the same channel:

1. install.sh gains a Phase 2.6 that either chains to Understand-Anything's upstream installer (`curl … install.sh | bash -s claude`) or, if the user is offline / wants minimal external calls, prints a "to install later" line.
2. No new CI/CD pipeline required — j-stack has none today, this stays consistent.
3. Upgrade path: re-run `bash install.sh` (idempotent for Understand-Anything per its own README).
